# Журнал решений: Module 0 (interproc)

Формат записи: **дата — решение — почему — альтернатива, которую отклонили**.
Дополняется по ходу реализации. План: [PLAN_INTERPROC_INLINING.md](PLAN_INTERPROC_INLINING.md).

---

## 2026-08-15 — Стартовые решения (зафиксированы на этапе плана)

### D-001. Два представления кода в юните вместо одного
`AnalysisUnit` несёт `code_for_gnn` (инлайненный, под бюджет токенов) и
`code_for_sandbox` (компилируемый bundle без инлайна).
**Почему:** Module 1 нужен только поток токенов, Module 3/4 реально компилирует код.
Семантически битый инлайн дал бы `harness_compiled=False` и выродил бы все вердикты в NEUTRAL.
**Отклонено:** одно общее представление (как в исходной идее) — ломает execution-based verification.

### D-002. Бюджет считаем настоящим токенизатором GraphCodeBERT
**Почему:** `predict_single` режет вход на `block_size-2 = 398` BPE-токенов молча;
оценка по символам ошибается в 1.5–2 раза на C-коде.
**Отклонено:** эвристика «символы/4».

### D-003. Приоритизация call-site вместо голого DFS
Порядок инлайна определяется score (sink в теле, аргумент выведен из параметров корня,
размер, глубина).
**Почему:** при потолке 398 токенов порядок обхода определяет, что именно увидит модель.
**Отклонено:** обход в порядке появления вызовов — тратит бюджет на первый попавшийся callee.

### D-004. Sink-функции и источники ввода никогда не инлайним
Список из `analysis/taint.py: DANGEROUS_SINKS + INPUT_SOURCES` + libc/STL.
**Почему:** это те самые токены-признаки, на которых обучена модель.
**Отклонено:** инлайнить всё, что нашли в проекте.

### D-005. Тривиальность корня определяется не длиной
Корень отбрасывается только если одновременно: нет вызовов, нет sink'ов,
нет операций с памятью и он короче `root_min_tokens`.
**Почему:** голый порог по длине выбросил бы однострочник вида
`void copy_data(char*d, const char*s){ strcpy(d,s); }` — то есть саму уязвимость.

### D-006. Работаем с байтовыми диапазонами исходного текста, а не печатаем AST обратно
**Почему:** (1) у tree-sitter нет генератора кода; (2) любой принтер переформатирует код
и уводит токены от обучающего распределения; (3) карта происхождения получается бесплатно.
**Отклонено:** трансформация AST + pretty-print.

## 2026-08-15 — Решения, принятые в ходе реализации

### D-007. Fallback-парсер — лексический, а не регулярочный
Вместо regex-эвристик (как в `analysis/taint.py`) написан модуль `interproc/clex.py`:
однопроходный классификатор символов исходника на код / строку / комментарий /
препроцессорную директиву, поверх него — сопоставление скобок и поиск определений функций.
**Почему:** для склейки по байтовым диапазонам нужны **точные** границы. Регулярка не умеет
сопоставлять вложенные скобки, спотыкается на `{` внутри строкового литерала и на
`)` внутри комментария — то есть даёт неверные смещения, а неверное смещение = битый текст
на выходе, а не просто пропущенная функция.
**Цена:** ~300 строк своего кода вместо 30 строк регулярок.
**Следствие:** модуль полноценно работает **без единой новой зависимости**;
tree-sitter становится улучшением точности, а не условием запуска.

### D-008. Единый движок замен: инлайн, переписывание `return` и переименование — один механизм
Все три операции выражаются как «заменить байтовый диапазон [start,end) на список сегментов»
и применяются одним проходом слева направо.
**Почему:** иначе пришлось бы пересчитывать смещения после каждой операции — источник
трудноуловимых багов. Дополнительно это даёт единое место для разрешения конфликтов
вложенных диапазонов.

### D-009. Вложенные вызовы `f(g(x))`: применяем внешний, внутренний отбрасываем
При пересечении диапазонов замен побеждает та, что имеет больший score; вложенная
записывается в `skipped` с причиной `nested`.
**Почему:** два пересекающихся диапазона нельзя применить одновременно.
Внутренний вызов при этом не теряется полностью — его текст попадает в связывание
параметра внешнего вызова.

### D-010. Каждое тело функции разворачивается в собственном координатном пространстве
Рекурсия работает так: тело `g` полностью разворачивается в координатах `g`, и уже
готовый список сегментов вставляется в точку вызова внутри `f`.
**Почему:** смещения никогда не «едут» между уровнями вложенности.

### D-011. Переименование локальных переменных — только при реальной коллизии
Кроме замены вхождений идентификаторов в теле, подстановка применяется и к текстам
аргументов вложенных вызовов (они извлекаются из того же тела).
**Почему:** в режиме `format="uni"` узел графа = уникальный токен; лишние имена вида
`buf_i1` раздувают словарь и уводят распределение.

### D-012. `--build-units-only` в `scan_cli.py` + отдельный `python -m interproc.cli`
Два входа в один и тот же код: флаг в основном CLI (сборка юнитов без запуска сканера)
и самостоятельный CLI модуля.
**Почему:** заказчик просил возможность проверить разбиение проекта изолированно,
до интеграции с ReGVD.

### D-013. Глубина задаётся `--inline-depth` (`InliningConfig.max_depth`), значение по умолчанию 2
`0` обязан давать текст, побайтово равный исходной функции — это регрессионный инвариант
и первый тест.

### D-014. `return` в callee: переписываем ключевое слово, а не тело
`return expr;` → `__r_<имя> = expr;` если значение вызова используется, иначе → `expr;`.
Объявление временной переменной ставится перед вставленным блоком.
**Почему:** минимальное вмешательство в текст, сохраняется исходное форматирование
выражения. Поток управления при раннем `return` при этом ломается — осознанный компромисс,
допустимый только потому, что для песочницы используется отдельное, неинлайненное
представление (D-001).

### D-015. Не инлайним функции с метками/`goto`, `asm`, `setjmp`, varargs
**Почему:** для меток нужно переименование с учётом области видимости, для varargs
невозможно связать параметры. Все случаи фиксируются в `skipped` со своей причиной,
то есть видны в статистике, а не молча теряются.

### D-016. Кэш разбора на диске, ключ включает версию парсера
Ключ: `(относительный путь, размер, mtime_ns, sha1[:16], parser_version)`.
**Почему:** без кэша повторный прогон по большому репозиторию каждый раз парсит всё заново.
Версия парсера в ключе — чтобы при правках backend'а кэш инвалидировался сам.

### D-017. Правило видимости 3b: определение видно через общий заголовок
Обычная раскладка C — прототип в общем `.h`, определение в `.c`, который вызывающий
никогда не включает. Формально «включённых файлов» правило такое определение не находит.
Добавлено правило: кандидат считается видимым, если include-замыкания вызывающего и
кандидата пересекаются **и** имя объявлено как прототип.
**Почему:** без него `main.c → util.c` через `util.h` резолвился как `exact_global`
(то есть «нашли по имени во всём проекте»), а не как честная видимость. На проекте с
одноимёнными функциями это привело бы к неверному выбору.
**Проверено:** `p01_simple`, резолюция сменилась с `exact_global` на `exact_include`.

### D-018. Функция с незакрытым телом восстанавливается, а не отбрасывается
Если у тела нет закрывающей скобки до конца файла, функция берётся до конца текста
и помечается флагом `truncated_body`. Такая функция может быть корнем, но **никогда**
не инлайнится в другие.
**Почему:** обнаружено на реальных данных — в датасете Devign 7 записей из 400
физически не имеют закрывающих скобок (например запись #273: `{`=1, `}`=0).
До этого правила parse rate на реальном корпусе был 98.25%, после — 100%.
Инлайнить незакрытое тело нельзя: получится синтаксический мусор.

### D-019. Причины отказа графового уровня попадают в отчёт юнита
`never_inline`, `ambiguous`, `macro`, `external`, `unresolved` записываются в
`AnalysisUnit.skipped` наравне с решениями самого инлайнера.
**Почему:** иначе по отчёту невозможно отличить «вызов оставлен намеренно»
от «вызов вообще не рассматривался». Для `strlen`/`printf` это принципиально:
их пропуск — сознательное решение (D-004), и оно должно быть видно.

### D-020. Стратегия `bfs` реализована как «предпочтение малой глубины»
Настоящий послойный обход потребовал бы переписать рекурсивное разворачивание.
Вместо этого `bfs` — это ранжирование по score с утроенным штрафом за глубину.
**Почему:** даёт наблюдаемо иное поведение для ablation при несоизмеримо меньшей
сложности. Честно зафиксировано, что это не канонический BFS.

## 2026-08-15 — Измерения на реальных данных

Стресс-тест: 400 функций Devign (реальный код QEMU/FFmpeg), разложенные по 20 файлам.

| Метрика | Значение | Комментарий |
|---|---|---|
| parse rate | 100% (393 функции) | после D-018 |
| время | 0.21 с на 400 функций | ~1900 функций/с |
| средний размер функции | ~347 токенов (оценка) | **при бюджете 398** |
| units truncated | 94 из 388 (24%) | четверть функций Devign сама не влезает в окно |
| unresolved вызовов | 88% | ожидаемо: функции вырваны из разных проектов, определений в корпусе нет |

**Главное следствие для статьи:** средняя функция Devign уже занимает ~87% окна
детектора, а 24% функций не влезают вовсе — ещё до всякого инлайнинга. Это
количественно подтверждает риск, заложенный в §9 плана, и означает, что
приоритизация call-site (D-003) — не оптимизация, а необходимое условие
работоспособности модуля. Замер сделан оценочным токенизатором; на настоящем
BPE значения будут выше, то есть картина хуже.
